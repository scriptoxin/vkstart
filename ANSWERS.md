# Замер времени загрузки рейтингов (Задание 2)

## Результаты измерений

Измерения проводились на списке приложений из каталога сервера (41 приложение), где каждый сетевой запрос рейтинга имеет эмулируемую задержку в 1500 мс (`delay(1500)`).

| Способ загрузки | Время выполнения (для 41 приложения) | Описание |
|---|---|---|
| **Последовательно** (`loadRatingsSequentially`) | **61 542 мс (~61.5 сек)** | Каждый рейтинг запрашивается по очереди после завершения предыдущего |
| **Параллельно** (`loadRatingsInParallel`) | **1 518 мс (~1.5 сек)** | Все рейтинги запрашиваются одновременно через `async` + `awaitAll()` |

---

## Выводы

1. **Разница по времени**:
   - Последовательная загрузка занимает суммарное время всех задержек ($N \times 1500\text{ мс} = 41 \times 1500\text{ мс} \approx 61.5\text{ сек}$).
   - Параллельная загрузка выполняет независимые корутины одновременно, поэтому общее время выполнения ограничено временем выполнения самого длинного одиночного запроса ($\approx 1.5\text{ сек}$).

2. **Ускорение**:
   - Использование параллельной загрузки через `coroutineScope` с `async` и `awaitAll()` дало **ускорение более чем в 40 раз**.

3. **Практическое применение**:
   - Для нескольких независимых асинхронных операций (например, получение дополнительных данных/рейтингов/изображений для элементов списка) всегда следует использовать параллельный запуск корутин через `async` и дожидаться результатов с помощью `awaitAll()`. Это существенно улучшает UX и уменьшает время ожидания пользователя.
